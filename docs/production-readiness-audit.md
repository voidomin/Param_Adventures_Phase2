# Production Readiness Audit & Release Plan

**Audit revision: v3** (rounds: 2026-07-28 initial pass → re-verification pass → deep pass on auth completeness/env separation, same day)
**Current app version:** `1.0.2`
**Implementation status:** Release 1 (`v1.1.0`), Release 2 (`v1.2.0`), and Release 3 (`v1.3.0`) shipped on branch `fix/release-1-correctness-hotfixes` — not yet merged to `main`. Every optional-feature credential introduced across these releases (Google Sign-In client ID, Turnstile site/secret keys, Resend webhook secret, audit-log retention days) is now configurable live from the admin Settings pages (Security / Integrations / Communications / System tabs) — no redeploy needed to set or rotate any of them. The `.env.example` entries for these are bootstrap fallbacks only, read when the corresponding DB setting has never been configured; the DB value always wins once set. (The admin IP allowlist that was briefly part of this list was removed at the client's request — see the auth-hardening item below.)

**Still outstanding on the client/ops side:** the code for Google Sign-In, Turnstile, and the Resend webhook is live but does nothing until each credential is actually entered, and `/api/health` isn't paging anyone yet. See `docs/pending-credentials-checklist.md` for the full punch list of keys to obtain and external setup steps — that file is the single source of truth for this, kept separate from the code-level tracking below so it doesn't get lost in the release-by-release detail.

Full-app pass across security, compliance, performance, testing, accessibility, booking/payment correctness, and tech debt. Supersedes the stale items in `docs/todo.md` (which still claims no cancellation/refund endpoint exists — it does now).

Rather than fixing items 5–10 at a time in priority order, this plan groups everything into six shippable releases by **effort, risk, and dependency** — each release is a coherent, testable unit rather than a grab-bag. Work through releases in order; within a release, order doesn't matter much.

## How to use

- Ship one release at a time. Each has its own PR(s), its own test pass, its own deploy.
- Check items off as they land; note the commit/PR like `docs/bugs.md` does.
- If something turns out to already be fine on closer look, mark `Won't Fix` with a one-line reason instead of deleting the row.
- This is a living document — each audit round is appended to the revision note above, not silently overwritten, so we can see what's been re-checked and when.

## Release 1 — `v1.1.0` Correctness Hotfixes

Small, isolated, backend-only fixes. No schema changes, no new UI, low regression risk. Ship this first and fastest.

- [x] **Logout doesn't revoke the session.** `src/app/api/auth/logout/route.ts` only clears cookies — never increments `tokenVersion`. A stolen access/refresh token stays valid until it naturally expires even after the user logs out. (Nuance: `tokenVersion` *is* already bumped on password change and on admin role changes — there's just no standalone "revoke session" step wired into the logout button itself.) Fix: increment `tokenVersion` in the logout handler too. — **Fixed**: added `revokeSessionFromToken()` in `src/lib/auth.ts` (decodes the refresh/access token ignoring expiry, bumps `tokenVersion`, silently no-ops on a missing/invalid token) and wired it into the logout route.
- [x] **Admin "delete booking" can silently leak a seat, with no guard at all.** `DELETE /api/admin/bookings/[id]/route.ts` fetches only `{ id: true }` — it doesn't even check the booking's status before soft-deleting it. A `CONFIRMED` booking can be archived directly from the admin panel with zero effect on `remainingCapacity`, permanently short-changing that slot's inventory even though the seat is actually free. Fix: either block deleting a `CONFIRMED` booking outright (force admins through the existing cancel/refund flow, which does restore capacity), or restore capacity inline on delete. — **Fixed**: now blocks deletion of a `CONFIRMED` booking with a 409, directing admins through the existing cancel/refund flow instead.

## Release 2 — `v1.2.0` Account Security & Auth Completeness ✅ Shipped

Everything here touches the login/register/admin-auth path — bundled for one coordinated QA pass instead of several. Grew from 2 items to 6 after a deeper pass specifically on authentication.

- [x] **No email verification.** `User.isVerified` defaults `false` on the schema, but nothing sends a verification email and nothing checks the flag at login — there is no verification-sending infrastructure anywhere in the codebase, not just an unenforced check. Anyone can register with an email they don't own and use the app immediately. — **Fixed**: registration generates a token (`emailVerificationToken`/`emailVerificationTokenExpiry`), emails a verify link (`/verify-email`), and creating a booking is blocked with a 403 until the account is verified. A persistent banner (`EmailVerificationBanner`, with a resend action) shows site-wide until verified.
- [x] **No admin 2FA.** SUPER_ADMIN and staff accounts — full access to customer PII and payment data — were password-only, with no MFA. This is the single account tier most worth hardening further. — **Fixed**: TOTP-based 2FA (enroll/confirm/disable + one-time backup codes) available to any account via Settings, enforced as a second login step once enabled. **2FA is opt-in for every account, never required** — `twoFactorEnabled` defaults `false`, so a brand-new sign-up goes straight through to booking with no added step. A dismissible, lowest-priority suggestion banner (`TwoFactorPromptBanner`) nudges users toward turning it on, deferring to email-verification/profile-completion prompts and permanently dismissible (localStorage, not per-session) so it doesn't nag. (An IP-based network allowlist for `/admin` was also built and shipped briefly, but removed at the client's request — the team works from mobile/changing networks, where a static allowlist causes more lockout risk than security benefit.)
- [x] **No Google Sign-In, despite a schema column reserved for it.** `User.googleId` exists in the database (`prisma/schema.prisma:46`, marked `@unique`) and `docs/data-schema.md` explicitly labels it *"For Google OAuth (future)"* — but no OAuth flow was ever built: no callback route, no client-ID wiring, no "Continue with Google" button on login/register. This is a genuine missing feature, not just hardening — social login is a standard, low-friction expectation for a consumer booking app in 2026, and it would also sidestep the email-verification gap above (Google-verified emails are trustworthy by construction). — **Fixed**: `POST /api/auth/google` verifies the Google ID token server-side (`google-auth-library`), links/creates the account (pre-verified, since Google already confirmed the email), and issues the same session cookies as password login. "Continue with Google" added to both login and register. Client ID is set once via Settings → Integrations → "Google Sign-In" — read fresh from the DB on both the server (verification) and client (the button fetches it from `/api/settings/public` at runtime) so rotating it never needs a redeploy. **Needs your action**: obtain and enter the Client ID — tracked in `docs/pending-credentials-checklist.md`.
- [x] **No per-account brute-force lockout.** Login attempts are throttled only by IP address (`authLimiter`, 20/min) — there is no counter tied to the target *email*, and no account lockout after N failed attempts. An attacker distributing login attempts across many IPs (or simply spoofing the `x-forwarded-for` header, which the rate limiter trusts as-is) faces zero per-account protection. — **Fixed**: `failedLoginAttempts`/`lockedUntil` on `User` — 10 failed attempts locks the account for 15 minutes regardless of source IP. (Threshold raised from an initial 5 to 10 after client feedback — 5 was judged too easy for a legitimate user to trip by accident.)
- [x] **No password complexity requirement.** Both registration and password-reset only enforce a minimum length of 8 characters (`z.string().min(8, ...)`) — no character-variety requirement. A password like `"aaaaaaaa"` is currently accepted. — **Fixed**: shared `passwordSchema` (`src/lib/validators/auth.schema.ts`) now requires 8+ characters with at least one uppercase, one lowercase, and one digit; used by both registration and password-reset.
- [x] **No admin session idle timeout.** Admin/staff sessions use the same JWT expiry as regular customer sessions, with no shorter-lived token and no client-side inactivity auto-logout for the highest-privilege account tier — worth a stricter timeout given what admin accounts can access. — **Fixed**: `useIdleLogout` hook auto-signs-out admin users after 45 minutes of no mouse/keyboard/touch activity, wired into `src/app/admin/layout.tsx`. Also added a global session watchdog (`src/lib/session-watchdog.ts`) wired into `AuthContext` — if *any* API call anywhere in the app reports the session is dead (expired/revoked token, deactivated account), the app now logs out and redirects to `/login` immediately instead of leaving a stale page for the next click to surface a raw error against.

## Release 3 — `v1.3.0` Compliance & Observability ✅ Shipped (2 items need your action)

None of these touch booking/payment logic — safe to batch together and ship independently of Releases 1–2.

- [x] **No cookie-consent banner, and analytics scripts fire unconditionally without one.** `registerSchema` also has no `termsVersion`/`acceptedTermsAt` capture at signup. Worse than a missing banner alone: `src/app/layout.tsx` renders Google Analytics, Meta Pixel, and Microsoft Clarity unconditionally on every page load once enabled in admin settings — `GoogleAnalytics.tsx` even *defaults to enabled* if its settings row doesn't exist. So today, personal browsing data is sent to three third-party trackers for every visitor with zero consent gate. Relevant to India's DPDP Act and IT Rules, and also makes the refund/cancellation policy harder to enforce contractually without a recorded agreement. — **Fixed**: `CookieConsentBanner` (Accept All / Reject Non-Essential) sets a `cookie_consent` cookie; all three analytics server components now read it via `next/headers` and render nothing until accepted (`src/lib/cookie-consent.ts`). Registration now requires an explicit "I agree to the Terms & Privacy Policy" checkbox, recording `termsVersion`/`acceptedTermsAt` on `User`; Google Sign-In records the same (no interactive checkbox exists for one-click OAuth, so both login/register pages carry a "by continuing you agree..." disclaimer next to the Google button instead).
- [x] **No public disclosure of the registered legal entity name or GSTIN.** The site footer shows an office address and support contact, but no legal entity name (the footer/copyright uses only the brand name) and no GSTIN anywhere on the public site (footer or `/contact`). GSTIN is only entered as an optional admin setting and, if filled in, surfaces on a post-purchase invoice PDF — never on the storefront itself. India's Consumer Protection (E-Commerce) Rules expect this kind of seller identity to be disclosed upfront, not just after checkout. — **Fixed**: `Footer` now displays the existing admin-configurable `companyName`/`gstNumber` platform settings (same ones already used for invoices) next to the copyright line. No new settings needed — just fill them in under Admin → Settings → Finance if not already done for invoicing.
- [x] **No retention/purge policy for audit logs or other non-account PII.** `AuditLog` rows accumulate indefinitely with no TTL and no purge job — separate from (and unaddressed by) the user-initiated account-deletion feature already built. DPDP's purpose-limitation principle expects data to be kept only as long as needed for its stated purpose. — **Fixed**: `POST /api/admin/audit-logs/purge` deletes rows older than the "Audit Log Retention" setting (Settings → System, default 365 days), run nightly via `.github/workflows/purge-old-audit-logs.yml`, same cron-secret auth pattern as the abandoned-booking cleanup job.
- [x] **No documented rollback procedure.** `docs/DEPLOYMENT.md` covers setup, deploy, and troubleshooting, but has no section on reverting a bad production deploy (e.g. Render's "redeploy previous" flow). Cheap to fix — this is a documentation task, not code. — **Fixed**: new "Rollback Procedure" section in `docs/DEPLOYMENT.md` covering Render, AWS App Runner, and migration-rollback caveats.
- [x] **Backup restore has never been tested.** We've confirmed Render's paid Postgres plan takes automated backups, but there's no documented restore drill anywhere — a backup that's never been test-restored is an assumption, not a guarantee. — **Documented**: new "Backup & Restore" section in `docs/DEPLOYMENT.md` with a step-by-step restore-drill procedure. This is a process doc, not code — **someone still needs to actually run the drill** at least once; the doc doesn't do that for you.
- [x] **Sentry isn't called from any API route.** Wired into React error boundaries only. Server-side failures (webhook errors, payment errors) are `console.error`-only — no alert when something breaks in production. — **Fixed for the highest-risk routes**: the existing `logError()` helper (`src/lib/monitoring.ts` — already had a DB kill-switch, just wasn't being called anywhere) is now wired into the payment webhook, booking creation, booking cancellation, refund updates, balance payment, and login catch blocks. Deliberately scoped to payment/auth-critical paths rather than all ~100+ routes — extend the same one-line pattern to more routes as needed.
- [ ] **`/api/health` isn't wired to any external monitor.** Real DB check exists, but no UptimeRobot/Better Uptime config, no `healthCheckPath` in `render.yaml`. If the site goes down, nothing pages anyone. — **Partially fixed**: added `healthCheckPath: /api/health` to `render.yaml` so Render itself uses it for deploy health/zero-downtime rollover. **Still needs your action**: this doesn't get anyone paged — sign up for UptimeRobot/Better Uptime (or similar) and point it at `https://<your-domain>/api/health` to actually close this gap. Tracked in `docs/pending-credentials-checklist.md`.
- [x] **No bounce/complaint handling for transactional email.** A bounced password-reset or booking-confirmation email fails silently — no retry, no alert. — **Fixed for Resend**: `POST /api/webhooks/email` verifies the Svix-signed payload and logs bounce/complaint/delivery-delay events to the audit trail + Sentry. Opt-in (Settings → Communications, shown only when the active provider is Resend), only covers the Resend provider — one of three configurable email providers (see `src/lib/email/factory.ts`); SMTP/Zoho bounce visibility would need a different mechanism. **Needs your action**: add a webhook pointing at `/api/webhooks/email` in the Resend dashboard if Resend is (or becomes) the active provider — that dashboard-side step can't be automated from here. Tracked in `docs/pending-credentials-checklist.md`.
- [x] **No CAPTCHA/bot protection** on `/register`, leads, or quote forms — rate-limiting is the only defense against scripted abuse. — **Fixed**: Cloudflare Turnstile wired into `/register` and the custom-trip lead form, opt-in via Settings → Integrations → "Turnstile" (both site and secret key unset by default — zero effect until configured; the site key is fetched by the browser button at runtime via `/api/settings/public`, not baked into the build). Note: `/api/quotes` turned out to be a GET-only "random inspirational quote" display endpoint, not a form — the only real public form beyond registration is the lead-capture form, which is covered. **Needs your action**: obtain and enter the Site/Secret Key pair — tracked in `docs/pending-credentials-checklist.md`.

## Release 4 — `v1.4.0` Payments Decision + Performance ✅ Shipped (E2E tests deliberately deferred)

Opened with three things only the client/ops team could verify or decide — all three resolved 2026-07-29 (live keys confirmed, DB separation confirmed, refunds staying manual by design). All remaining items shipped the same day except E2E test setup, deferred as a separate, larger effort by client decision.

- [x] **Verify with ops: confirm Razorpay is running live keys, not test keys.** `docs/todo.md` still has "Switch Razorpay from test mode to live mode" unchecked. The code itself has no unsafe fallback (dummy keys are hard-gated to `development`/`test` environments only), so this was purely a matter of confirming which key string (`rzp_live_...` vs `rzp_test_...`) is actually configured in the production environment. — **Confirmed by client (2026-07-29): production is running live keys.** No code change needed.
- [x] **Verify with ops: staging and production database separation relies entirely on operator discipline, with no automated safeguard.** Deployment docs describe Render (staging/UAT) and AWS (production) as separate targets, each with its own manually-entered `DATABASE_URL` — but nothing in code prevents both being pointed at the same database by mistake (no environment-name assertion at boot, no DB-name check). — **Confirmed by client (2026-07-29): staging and production are separate databases today.** Client opted not to add a boot-time guard on top of this for now — revisit if the team grows or deploys become less centralized.
- [x] **Decision needed: refunds are never automatically sent back via Razorpay.** When a customer cancels a paid booking, the system correctly computes the refund and restores slot capacity — but settlement is 100% manual: an admin either issues internal `TravelCoupon` credit or hand-records a UTR for a bank transfer. No `razorpay.payments.refund()` call exists anywhere. — **Won't Fix (client decision, 2026-07-29): stays manual, by design.** Admin-driven settlement (internal credit or hand-recorded bank transfer) is the intended flow, not a gap to close.
- [x] **Public + admin experiences lists have no pagination.** Both load the entire table on every request. Fine at current catalog size, will not stay fine. — **Fixed for admin, capped for public (client decision, 2026-07-29):** the admin list (`/admin/experiences`, `/api/admin/experiences`) now has real server-side pagination (`page`/`limit` query params, `{ experiences, pagination: { total, page, limit, totalPages } }` response shape, Prev/Next controls) — same pattern as `/admin/users`. The public `/experiences` page was deliberately **not** converted to server pagination: it currently filters/sorts its entire dataset client-side for instant feedback with no network round-trip per filter change, and the client opted to preserve that UX rather than trade it for real pagination. Instead both the public API route and the page's direct Prisma query now cap at `take: 300` as a safety net against unbounded growth — same "capped, not paginated" trade-off the admin list used before this fix. Revisit with real server-side filtering if the catalog approaches that cap.
- [x] **Missing composite DB index for the abandoned-booking cleanup query.** It filters `bookingStatus + paymentStatus + createdAt` together but only single-column indexes exist. Add `@@index([bookingStatus, paymentStatus, createdAt])`. — **Fixed**: added via migration `20260729055105_add_booking_cleanup_composite_index`.
- [x] **No CI step validates migrations before deploy.** `render.yaml`'s `preDeployCommand` runs `prisma migrate deploy` directly against production with no dry-run/diff gate first. — **Fixed**: new `migration-check` job in `.github/workflows/sonar.yml` spins up an ephemeral Postgres service container, runs `prisma migrate deploy` against it from scratch (the same command production runs), then `prisma migrate diff` to confirm `schema.prisma` has no un-migrated changes. Runs on every push/PR alongside the other CI jobs.
- [ ] **No E2E tests.** No Playwright/Cypress setup exists. Unit/integration coverage is otherwise strong (1359 tests, all major feature areas covered). Deliberately out of scope for this release (client decision, 2026-07-29) — a larger effort than the rest of this batch; revisit separately.
- [x] **Staging config lives outside version control.** Only one `render.yaml` in-repo (production blueprint); parity risk if staging drifts unnoticed. — **Fixed**: added `apprunner.yaml` at the repo root as the version-controlled AWS App Runner config (mirroring `render.yaml`'s role for Render), and clarified in `docs/DEPLOYMENT.md` that both providers auto-detect their respective in-repo blueprint files rather than relying on manual dashboard configuration for build/run commands.
- [x] **Double-submit on "Pay Now" has no formal idempotency key.** Current protection (UI state swap + server-side superseding of prior pending bookings) works, but a fast double-click could still start two Razorpay orders before the button visually disables. — **Fixed**: added a synchronous ref-based guard on the Pay Now button (`BookingModal.tsx`) and the balance-payment button (`bookings/page.tsx`) that closes the same-tab double-click race immediately, no re-render needed. On top of that, a client-generated `idempotencyKey` is now sent with every booking-creation request and stored on `Booking` (plain index, not unique — see migration `20260729055739_add_booking_idempotency_key`); a repeat request under the same key while the original booking is still pending or already confirmed returns that booking/order instead of creating a duplicate, covering multi-tab clicks and network-level retries that a same-tab ref guard can't catch. A retry after a genuine failure (booking ends up `CANCELLED`) is unaffected and creates a fresh booking under the same key.
- [x] **Generic user uploads (avatar, review photos) aren't compressed client-side**, unlike admin-uploaded trip images. — **Correction, not a fix**: investigation found the premise was half wrong. Avatar uploads already go through the same canvas-based crop-and-recompress step (`ImageCropper.tsx`, re-encodes to JPEG @ 0.95 quality, caps the longest edge at 1600px) that admin trip images use — it was never sent raw. Review photos, on the other hand, aren't a feature that exists at all today (no photo attachment UI on reviews, just a rating and text) — there's nothing to compress because there's nothing to upload. No code change made; if photo attachments on reviews are wanted as a new feature, that's a separate scoping conversation, not a compression fix.

## Release 5 — `v1.5.0` UX & Accessibility Polish ✅ Shipped (client-facing modals only; admin panel modals deferred)

Lowest risk, most visible to end users, no urgency — good candidate for a quiet release between feature work.

- [x] **Modals have no focus trap or Escape handling** (confirmed on the account-deletion modal, likely true elsewhere — worth a sweep). — **Fixed for the 8 customer-facing modals** (account-deletion, `BookingModal`, `CancelModal`/`PayBalanceModal` on `/bookings`, `EditGuestModal`/`CancelGuestModal`/cancel-success on the guest-edit page, and the itinerary-download lead-capture modal). Built one shared `Modal` component (`src/components/ui/Modal.tsx`) on top of `@headlessui/react`'s `Dialog` — already an installed-but-unused dependency — which gives Escape-to-close and a real focus trap (tab cycling confined to the panel, focus restored to the trigger on close) for free, replacing hand-rolled `fixed inset-0` divs with none of that behavior. **Client decision (2026-07-29): the remaining ~19 admin-only modals stay as-is for now** — same sweep would apply cleanly since the shared component already exists, just not done in this pass.
- [x] **Booking/payment page surfaces raw error text and uses native `alert()`** instead of the toast pattern used elsewhere in the app. — **Correction + fixed**: no toast pattern actually existed anywhere in the codebase (the audit's premise was wrong on that point) — built one from scratch (`src/components/ui/Toast.tsx`, `ToastProvider`/`useToast`), success toasts as `role="status"`/`aria-live="polite"`, errors as `role="alert"`/`aria-live="assertive"` (replicating what native `alert()` gave for free: an interruptive screen-reader announcement). Migrated all 10 `alert()` calls on the booking/payment path (`bookings/page.tsx`, `DownloadInvoiceBtn.tsx`, `DownloadItineraryBtn.tsx`). **Client decision (2026-07-29): the ~30 `alert()` calls elsewhere in the admin panel stay as native alerts for now** — same toast system already exists to extend to them later.
- [x] **No loading skeleton for the experience detail page or any dashboard route** (admin already has good skeleton coverage; extend the same pattern here). — **Fixed**: added `src/app/experiences/[slug]/loading.tsx` (Next's file-based loading convention — this route is a Server Component with no client fetch to gate on, so this is the correct mechanism, unlike the dashboard routes below). Built `DashboardStatsSkeleton`/`DashboardListSkeleton`/`DashboardFormSkeleton` (`src/components/dashboard/DashboardSkeleton.tsx`) and swapped them into all 9 dashboard routes' existing `isLoading` conditionals, replacing bare `Loader2`/spinner placeholders — including the shared `DashboardLoader` used by both the manager and trek-lead list pages, fixed once in `DashboardShared.tsx` rather than per-page.
- [x] **A few images have unintentional empty `alt=""`** — looks like an oversight, not deliberate. — **Correction, not a fix**: audited all 4 `alt=""` instances in the codebase and every one is legitimate, not an oversight — a tracking-pixel `<img>` (`MetaPixel.tsx`), a decorative blurred background duplicate sitting right next to the real image with a proper `alt={exp.title}` (`experiences/[slug]/page.tsx`), and two cases where the image sits directly beside visible caption/title text (`SimilarTrips.tsx`, admin media-merge thumbnails) — WCAG treats a redundant image next to an equivalent visible text label as correctly decorative. No code change made.
- [ ] **No real-device mobile responsiveness testing** — stays a manual QA step, not CI-automatable.

## Already confirmed fine (no action needed)

Custom 404/500 error pages, `robots.txt`/`sitemap.xml`, GST-compliant invoicing, refund audit trail (`RefundRequest` + `AuditLog`), CSRF protection, rate limiting, security headers (CSP/HSTS/etc.), CI lint+typecheck+test gate, DB connection pooling, ISR caching/revalidation, ~zero TODO/FIXME comments, no dead code, auth logic consistently centralized, concurrent-booking race protection (Serializable isolation on capacity decrement), manual-payment admin approval flow, coupon/credit reuse protection, abandoned-booking cleanup cron, DB backups (Render Postgres paid plan), self-service account deletion + data export (DPDP compliance), Razorpay webhook delivery-level deduplication (`ProcessedWebhookEvent` — verified wired in and working; an earlier pass in this audit incorrectly flagged it as dead code), dependency vulnerability scanning in CI (`npm audit --audit-level=high` genuinely fails the build on high/critical production-dependency issues on every push/PR; a secondary devDependency-inclusive scan on schedule/dispatch is informational-only, which is an acceptable tradeoff), **password-reset tokens are correctly single-use** (invalidated in the same transaction as the password change, with a `tokenVersion` bump on top — no reuse vulnerability).
